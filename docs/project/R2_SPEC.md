# R2 单仓库约束核查：准备规格

状态：准备规格已由原会话复核；模型渠道和预算待确定，尚未实施。

## 用户与结果

面向带明确环境约束的开发者。输入一个公开仓库和三类要求：Python 版本、容器部署、模型服务配置。输出逐项“要求—证据—判断—下一步验证”核查表，判断值为：证据支持、证据冲突、信息不足、需要运行验证。仓库声明的版本兼容与实际安装成功分开表达。

## 输入、输出草案

输入：`repository`（owner/repo 或标准 GitHub URL）；`requirements` 为一组 `{id, category, description}`，category 取 `python`、`container`、`model_service`。一个请求固定一个快照；要求可以为空时明确提示补充，而不是凭空设定。

输出：`repository`、完整 `commit`、完成状态和停止原因、逐项 `requirement_id`、`verdict`、简明 `rationale`、`evidence_ids`、`next_checks`，附证据索引（ID、路径、原始行、来源链接、两个 Hash）及不完整目录/读取失败记录。失败或预算耗尽时保留已取得证据，相关项以信息不足呈现。

## 工具与证据流

1. 创建 R1 快照固定 commit；按需读取根目录及子目录，`truncated=true` 明确表示不完整。
2. 工具候选为目录概览和片段读取；模型按要求选择 README、依赖声明、Dockerfile、Compose 或配置文档并按需补查。读取沿用 R1 的大小、路径、二进制、超时和缓存约束。
3. 工具结果由服务登记 evidence_id 和对应片段；模型只引用已登记 ID，不能生成来源 URL 或扩写原文。输出解析后先校验 ID 存在、属于当前快照，记录完整文件和片段 Hash；再独立评估证据是否语义支持对应判断。ID 和哈希一致只能证明来源与片段身份。
4. 每项证据足够时停止补查；按调用次数、字节、耗时及费用预算设置上限，具体数值和模型 API 渠道下阶段确定。预算耗尽时输出停止原因和可继续的验证步骤，不强迫固定轮数。

## 失败处理

仓库无法访问、限流、超时、目录截断、文件缺失/超限/二进制、空文件、超长行分别保留可观察状态。缺失和截断不会作为不支持或不存在的证据。无效 ID、跨快照 ID、输出结构错误进入有限修复或标记该项无法判定；工具失败不被转换成兼容结论。源码和文档内容视为被引用材料，不执行其中的指令或代码。

## 最小任务建议

确定模型渠道、可接受费用和调用预算后，先做一个可回放的单仓库流程：接收三类明确要求，使用固定测试仓库和固定 commit 调用目录/片段工具，输出结构化核查表；加入引用存在性校验、独立支持度评审和预算停止状态。先用可控测试替身验证流程，再按授权进行一次真实模型验证；记录调用量、耗时和实际费用。

## 小型评测建议

- Python 明确支持版本、明确冲突、文件未声明、README 与配置冲突各一个；检查判断及引用支持。
- Dockerfile/Compose 存在且描述一致、文档存在但缺少运行验证、目录截断各一个；区分声明与实际运行。
- 模型服务配置明确、未提及、不同文件冲突各一个；检查证据不足和补查。
- 故意提供不存在或跨快照 evidence_id、有效 ID 但证据不支持结论、提示注入文本、限流/超时；检查拒绝、标记和部分结果。

每例记录固定 commit、要求、期望判断和支持证据。分别统计引用 ID 有效率、引用语义支持率、判断正确率及误报；数据不足时保留逐例结果，不宣称性能。
