# R2 演示与简历素材

## 基于现有实测可描述

实现公开 GitHub 仓库的固定提交证据读取：按目录浏览 UTF-8 文件，记录原始行号、文件与片段 SHA-256、稳定证据 ID 和固定版本链接；使用 SQLite 复用同版本缓存，并处理目录截断、大小限制、限流和超时。R1.1 的 Python 19 项、前端 6 项测试通过；Chrome 对真实公开仓库验证了固定版本读取、缓存、行号跳转和来源访问。

实现单仓库工程约束核查原型：设计 Responses API 工具调用循环，复用固定提交的目录和文本读取，为 Python、容器部署及模型服务要求生成带引用的核查表；限制每任务模型请求和工具调用次数，并校验引用是否属于本次读取，避免使用未登记的证据。

离线验证：Python 28 项、前端 6 项测试通过；使用模型替身覆盖连续工具回合、参数、无效引用降级、预算耗尽、信息不足和缺少密钥等情况，Chrome 使用替身走通输入、进度和结果表。这些结果可用于描述已实现的设计和测试。真实联调另完成两例：Python 3.11 工作流配置获得原文支持；Ollama 配置要求返回信息不足，人工逐项核对引用与判断。两个案例输入 18,929、输出 574 tokens，费用估算及语义核对详见 [真实案例记录](R2_REAL_VALIDATION.md)。

## 两分钟演示脚本

1. （20 秒）说明问题：开发者有具体 Python、容器或模型配置要求，需要依据仓库固定版本中的原文判断。
2. （20 秒）输入一个公开仓库和明确要求，启动核查；说明快照 commit 固定，工具只能读取该仓库的目录与文本片段。
3. （30 秒）展示工具进度：查看目录、读取文件、按缺口继续读取；说明模型请求与工具调用有上限。
4. （35 秒）展示要求、证据、判断、下一步验证表；打开证据来源和原始行号。说明引用 ID 校验其存在和属于本次读取，语义是否支持由人工逐项对照来源原文检查。
5. （15 秒）展示信息不足案例与停止原因，区分仓库声明和运行验证；展示实际调用用量及耗时。

当前两例已完成真实模型调用；费用为按公开单价与实测用量计算的保守估算，账户账单尚待核对。
